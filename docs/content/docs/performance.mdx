## Animate slots, not the tree

A `SharedValue` prop or a slot-backed
[`NodeHandle.set`](/api/interfaces/NodeHandle) patches native slot data on the UI
thread. Changing ordinary JSX props through React recompiles and uploads the
scene. An unslotted handle write also recompiles, but skips the React and Fabric
commits.

## Recommits snapshot animating values from shared memory

Every commit snapshots each `SharedValue` prop into the program, so the scene
draws correctly before the first UI-thread push. Reanimated 4 keeps a mutable's
value on the UI runtime and flags it dirty on every UI-side write, which makes
a JS-thread `.value` read of an animating value a synchronous hop to that
runtime, queued behind whatever frame the UI thread is in. A recommit of a
scene with N animating slots would be N such hops. Instead, the UI-thread
driver mirrors every value it pushes into shared memory, and a recommit whose
slots are already animating snapshots them from there with plain loads; a
recommit that lands before the driver's first push reuses the literals native
is already drawing. A value the commit has never seen is not read at all: the
program ships with placeholder literals and the view holds it until the
driver's first push lands, one UI frame later, so program and values draw
together. The same mirror backs a JS-thread `NodeHandle.set`. Without
Reanimated a commit reads each value directly, where a read is a plain
property.

## Batching is automatic — and order-aware

The GPU merges only *adjacent* compatible draws into one batch, so a sibling
list that interleaves shape kinds (`<Rect>`, `<Circle>`, `<Rect>`, ...) would
flush a pipeline batch at nearly every node. At scene commit, siblings whose
painted bounds provably don't overlap are re-clustered by batch class — once,
off the hot path, with pixel-identical output (overlapping draws are never
reordered, so paint order still wins where it can be seen). At 20k interleaved
nodes this cuts ~13k GPU batches a frame to ~1k and roughly quadruples the
presented frame rate. You still get the best batches by grouping same-kind
shapes yourself; the pass just stops interleaving from being a cliff.

## Keep children primitive

The reconciler recognises the exported drawings directly. A wrapper function
component falls back to the slower path.

```tsx
{/* fast */}
<Canvas>{shapes.map((s) => <Rect key={s.id} {...s} />)}</Canvas>

{/* falls back */}
<Canvas>{shapes.map((s) => <Star key={s.id} {...s} />)}</Canvas>
```

## Other levers

- `<Group picture>` records a static subtree once; dynamic children fall back
  to direct drawing.
- `<Group layer>` costs an offscreen surface — use it only for group opacity or
  group filters.
- Pool handles with [`createHandle`](/api/functions/createHandle) and toggle
  `visible` instead of mounting and unmounting.
- For large sprite or mesh collections, move to
  [`useSpriteBuffer`](/api/functions/useSpriteBuffer) or
  [`useVertexBuffer`](/api/functions/useVertexBuffer).
- One animated opacity per chain — see [Animation](/docs/animation).
- Under memory pressure, [`purgeCaches`](/api/functions/purgeCaches) drops the
  decoded-pixel and GPU caches immediately;
  [`getCacheInfo`](/api/functions/getCacheInfo) reports what they hold — see
  [Images § Cache](/docs/images#cache).

## Redraws are scoped to what a canvas actually reads

Decoded images and loaded typefaces live in process-wide registries, so a video
frame, a decode landing or a newly loaded face moves a counter every mounted
canvas can see. A canvas only reacts to the registry its own compiled scene
reads: one that draws no image is neither woken nor redrawn when an image
changes, and the same holds for text and fonts.

Nothing to configure, but it is worth knowing what it keys on. The scene is
treated as reading the image registry when it holds an `<TgfxImage>`,
`<CameraFrame>` or `<Atlas>`, an image handle, an `<ImageShader>`, or a runtime
shader or `<Blend>` whose child shaders sample an image; and as reading fonts
when it holds any text. A canvas built entirely from shapes, gradients and
image-free runtime shaders is therefore idle while a video plays beside it.

## Offscreen canvases do not draw (Android)

A canvas scrolled out of view keeps its surface, but Android skips its draws
entirely: animated values keep flowing into their slots, and the first frame
after the canvas scrolls back in picks them up. A canvas that never comes back
costs nothing per frame. Snapshots still render while hidden — `snapshot()` and
`save()` force the frame they need.

## Vulkan backend (Android)

The Android renderer runs on Vulkan by default; OpenGL ES remains one Gradle
property away:

```properties
# android/gradle.properties
TgfxVulkan=OFF
```

When Vulkan is on, the build links the Vulkan prebuilt (`android/libs-vulkan`, shipped alongside
the GL one; absent prebuilts fall back to compiling the vendored tgfx with
`TGFX_USE_VULKAN`), swaps the window glue to `VulkanWindow` / `VulkanDevice`,
and routes video frames through an `AImageReader` — a SurfaceTexture cannot
exist without a GL context. Video frames are converted
via a CPU plane copy and tgfx's own YUV shader: on at least Mali, the driver
ignores the color-range override on zero-copy external-format imports and
full-range video renders washed out otherwise.

Measured on a Galaxy F14 (90 Hz, Mali-G68), the same stress scene presents
roughly 15–30% more frames per second than the GL backend at GPU-bound loads,
at similar CPU and ~50 MB more PSS.

## Measure

With the repository's benchmark app installed and an Android device configured:

```bash
node benchmarks/renderer-benchmark/scripts/run-quick.mjs \
  --tag=mine --renderers=tgfx,thor-gpu,skia-graphite
```
